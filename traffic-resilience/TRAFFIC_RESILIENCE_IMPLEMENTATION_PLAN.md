## Stage 1: Rate limiting at the gateway
**Goal**: Add a Traefik `ratelimit` middleware to `user-service` (and/or `order-service`), same label-based pattern as the `forwardauth` middleware from the auth-service work.
**Success Criteria**: Requests under the configured rate pass through normally; requests bursting past it get `429 Too Many Requests` from Traefik, without reaching the backend.
**Tests**: Fire a burst of concurrent requests (e.g. via a small script or `hey`/`ab`) and confirm some are accepted, some are `429`.
**Status**: Complete (verified with `traffic-resilience/test-ratelimit.sh`, 20 concurrent requests -> 6 passed / 14 rejected against `average=2`, `burst=5`)

## Stage 2: Circuit breaking at the gateway
**Goal**: Add a Traefik `circuitbreaker` middleware so that if a backend starts failing/timing out under load, Traefik stops routing to it for a cooldown period instead of continuing to hammer a struggling service.
**Success Criteria**: Simulate a failing backend (e.g. `whoami` swapped for something that errors, or artificial delay) and observe Traefik trip the breaker and short-circuit further requests.
**Tests**: Force a failure condition, confirm requests start failing fast (short-circuited) rather than continuing to hit the backend once the threshold trips.
**Status**: Complete (built a controllable C# `user-service` replacing the `whoami` stub - see `user-service/UserService/Program.cs`, with `POST /admin/config {"failureRatePercent": N}` to inject real HTTP 500s. Switched the breaker expression from `NetworkErrorRatio()` to `ResponseCodeRatio(500, 600, 0, 600) > 0.30` since 500s are HTTP-level, not network-level, failures. Verified: 1 real 500 -> breaker trips -> subsequent requests get fast `503` with no backend call; after resetting failure rate to 0, observed the gradual half-open ramp - a mix of `503`/`200` before fully stabilizing back to `200`. Also learned along the way: `docker compose stop` deregisters the router entirely (404, not a network error); `docker pause` causes a hang with no timeout configured rather than a countable failure; and HTTP `serversTransports` defined via Docker labels were silently dropped by Traefik's docker provider in this version - confirmed via `--log.level=DEBUG` config dump - so that path was abandoned in favor of the controllable backend.)

## Stage 3: Discuss what's simplified vs. production
**Goal**: Compare this to how a real gateway/mesh would combine rate limiting + circuit breaking + retries + load shedding together, and where these controls would live in a Kubernetes/service-mesh setup (e.g. Envoy/Istio) vs. our single-Traefik-instance setup.
**Status**: Complete (full discussion captured in `traffic-resilience/PRODUCTION_COMPARISON_NOTES.md`)

**Summary**: our setup is a single Traefik instance enforcing rate limiting and circuit breaking at the edge, in front of one backend replica each - almost every gap traces back to "single instance, single replica, edge-only." Rate limiting is keyed on client IP by default (never configured `sourceCriterion`) and its state lives in one process, which would fragment across replicas at scale; production solves this with a shared external rate-limit service (Envoy's Lyft `ratelimit` pattern), the same "ask a shared authority" shape as our `forwardAuth`. Circuit breaking is scoped per-router (aggregating all backend replicas as one pool), whereas production splits this into two distinct mechanisms: per-endpoint outlier detection (ejects one bad replica while others keep serving) and resource-based circuit breakers (protect the caller from exhausting connections/requests to an upstream, with `maxRetries` deliberately coupled into the same config). We built zero retry logic and zero load shedding (a proxy's self-protection against its own resource pressure, e.g. Envoy's overload manager) - both real, separate concerns from what we covered. Most fundamentally, everything we built only protects north-south (edge) traffic; east-west (service-to-service) calls would bypass all of it entirely in our current setup, which is exactly why a sidecar/mesh model applies these same concerns at every hop, not just the edge - see the sidecar discussion in `CIRCUIT_BREAKING_NOTES.md`.

## Stage 4 (stretch goal): Shared external rate-limit service via gRPC
**Goal**: Build a standalone gRPC service implementing the "shared authority" rate-limit pattern from the Stage 3 discussion (Envoy/Lyft `ratelimit` style) - a `CheckRateLimit` RPC that returns allowed/denied, backed by shared state (in-memory to start, Redis as a further stretch) so the decision is consistent no matter how many callers/replicas ask. First real gRPC experience.
**Open design questions to resolve when starting**: Traefik's native `ratelimit` middleware has no built-in support for delegating to an external service the way `forwardAuth` does for auth - so how does this actually plug into the gateway? Options to weigh: (a) wrap the gRPC service behind a thin HTTP endpoint and reuse the `forwardAuth` delegation mechanism (same trick as `auth-service`'s `/validate`, just backed by gRPC internally instead of JWT logic), (b) call the gRPC service directly from a custom client/script without going through Traefik at all, just to prove out the gRPC mechanics first, or (c) investigate whether a Traefik plugin could speak gRPC natively. Decide deliberately rather than defaulting.
**Success Criteria**: Can demonstrate the same rate-limit decision being consistently enforced across what simulates multiple caller/replica instances, backed by one shared source of truth - directly solving the per-replica fragmentation problem identified in the Stage 3 discussion.
**Status**: Not Started
