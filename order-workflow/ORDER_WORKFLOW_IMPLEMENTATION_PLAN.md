## Stage 2: Backend data contention
**Goal**: Simulate two concurrent requests racing to update the same order (e.g. both trying to change its status at once) and observe the race play out unguarded first.
**Success Criteria**: Reproduce a visible race condition (lost update) with concurrent requests, then fix it with one of: optimistic concurrency (version/ETag check, reject stale writes), pessimistic locking (DB row lock), or a distributed lock (Redis) if state ends up shared across replicas.
**Status**: Complete. Reproduced the lost-update race unguarded (two concurrent `PATCH`es to the same order, different target statuses). Fixed with optimistic concurrency: `IOrderRepository.UpdateStatusAsync` now does a conditional `ExecuteUpdateAsync` (`WHERE id = @id AND status = @expectedCurrentStatus`), returns whether it actually affected a row; `UpdateOrderStatusCommandHandler` throws a new `OrderStatusConflictException` -> `409` when it didn't. Considered and rejected two alternatives: pessimistic locking (`SELECT FOR UPDATE`, optionally with `SKIP LOCKED` to fail-fast instead of blocking - concluded `SKIP LOCKED` just converges pessimistic locking's behavior toward what optimistic concurrency already gives for free) and Postgres's built-in `xmin` system column as a free row-version token (architecturally fine via a DTO in `Application/Interfaces`, but not worth the EF Core config overhead + Postgres-specific gotchas - wraparound, false conflicts from incidental touches, zero portability - for an entity with only one mutable field today). Verified twice concurrently: once with genuine overlap (`200`/`409`, no lost update), once without genuine overlap (`200`/`200`, a valid sequential `Shipped -> Cancelled` transition, not a bug) - confirming the specific original bug (two requests reading the same status and both silently succeeding) is no longer reproducible either way.

**Follow-up refinement - domain-level transition validity (a separate concern from concurrency)**: the `200`/`200` sequential case above surfaced a real gap - the concurrency fix guarantees "no update ever acts on stale data," but says nothing about whether a transition is *ever* legal (`Shipped -> Cancelled` succeeded with zero concurrency involved, which most real order systems would reject outright). Fixed at the Domain layer, not Infrastructure: `Order.Status` setter made private; `Order.EnsureCanTransitionTo(newStatus)` validates against an explicit `AllowedTransitions` table and throws `InvalidOrderStatusTransitionException` (defined in `Domain/`, since it's a domain invariant, not a persistence concern); `Order.ApplyStatusChange(newStatus)` is a separate mutating method called *only after* the DB write is confirmed to have succeeded. This ordering (validate -> persist -> apply-in-memory) was deliberately chosen over validate-and-mutate-immediately to avoid a real gap: mutating in-memory before confirming persistence would leave a "lying" object if the DB write then failed, requiring an explicit revert - the reordering removes the need for a revert entirely rather than adding one. `Order` gained an explicit constructor (`new Order(id, status, amount)`) since encapsulating the setters broke `CreateOrderCommandHandler`'s previous object-initializer syntax. Verified: shipping an order then attempting to cancel it correctly returns `409` with state left unchanged; a valid `Placed -> Cancelled` transition on a fresh order still works.

## Stage 4: Coordinate the full order -> payment -> ship workflow
**Goal**: Wire the three steps into one flow: place order (order-service) -> charge payment (payment-service) -> ship (ship-service).
**Coordination style — decided**: a real workflow engine, **Temporal**. Choreography was already effectively ruled out by Stage 6's own wording ("once Stages 4-5 work as synchronous orchestration... migrate to pub-sub" presupposes Stage 4 *is* orchestration). Between hand-rolled orchestration and Temporal, chose Temporal deliberately for the learning value (durable execution, first-class Activity retry policies, a real production-grade skill) - the same "reach for the deeper real tool" pattern as the gRPC rate-limiter and the Clean-Architecture-+-MediatR-+-Outbox choice for `order-service`. Temporal itself needs no changes to `payment-service`/`ship-service` - a Worker's Activities just call their existing REST endpoints over ordinary HTTP.
**Worker placement — decided**: a dedicated new `order-workflow-worker` service, matching how every other concern in this project got its own component.
**East-west resilience via sidecars - deferred to a later stage, explicitly not part of Stage 4**: Temporal's Activity retries already cover the order -> payment -> ship traffic, so a sidecar mesh here would be a deliberate learning experiment (same reasoning as Temporal/gRPC), not filling a gap - and it's being built later, on its own, not bundled into this stage. Historical reasoning preserved from the original discussion:
1. Route internal calls back through the gateway too (awkward - Traefik isn't designed for internal service-to-service routing).
2. Build resilience (timeouts/retries/circuit breaking) directly into the calling service's HTTP client - inferior even centralized into a shared library, since every service still has to *remember* to reference and correctly configure it (duplicated *usage*, not just duplicated code).
3. A lightweight local service mesh (sidecar model, e.g. Linkerd or hand-rolled per-service Envoy sidecars) - the production-correct answer in general (push the concern into infrastructure every call passes through, same principle as `auth-service` + `forwardAuth`), kept as a separate future experiment rather than folded into this stage.

### Stage 4c: The real OrderFulfillmentWorkflow
**Goal**: Define the actual workflow (place order already happened by the time this starts -> charge payment -> ship) with `ChargePaymentActivity`/`ShipOrderActivity`, each just making an ordinary HTTP call to `payment-service`/`ship-service`'s existing REST endpoints - no changes needed to either of those services.

Raised and discussed explicitly (not discovered later by accident). **Resolution: sidecar mesh work (previously an unscheduled "later" item) is promoted to the immediate next priority once Stage 4/5's basic flow works** - not deferred indefinitely. This is the concrete gap that work will close.
**Retry/timeout policy**: `StartToCloseTimeout` ~5s, `RetryPolicy` with a small `MaximumAttempts` (e.g. 3) per Activity - deliberately testable against `payment-service`'s existing `/admin/config` failure-rate knob so retry behavior can actually be observed in Temporal's event history, not just assumed to work.

Verified end-to-end via Temporal CLI: `order-test-1` completed with both real service responses embedded in the result string.

### Stage 4d: Trigger the workflow from order-service
**Goal**: `order-service` gets a Temporal *client* (not a worker) and starts the workflow automatically - most likely via a new `INotificationHandler<OrderCreatedEvent>` (alongside the existing `LogOrderCreatedEventHandler`), so creating an order automatically kicks off fulfillment.
**Success Criteria**: `POST /api/v1/orders` through the gateway results in a new workflow execution visible in Temporal Web UI, with no manual trigger needed.
**Status**: Complete. `order-service` doesn't share the compiled `OrderFulfillmentWorkflow` type with `order-workflow-worker` (separate deployables, matching the bounded-context principle from the earlier "shared entity across services" discussion) - `StartOrderFulfillmentWorkflowHandler` uses Temporal's untyped `StartWorkflowAsync("OrderFulfillmentWorkflow", object[] { orderId, amount }, ...)` overload, referencing the workflow by name/string only, same as the CLI has been doing all along. **Workflow ID = the actual OrderId** (`notification.OrderId.ToString()`) - deliberately, since Temporal enforces workflow-ID uniqueness among running executions, giving the same kind of dedup guarantee as the idempotency-key work, for free. `ITemporalClient` registered as a singleton via `AddSingleton<ITemporalClient>(await TemporalClient.ConnectAsync(...))` at startup. **Known minor risk, not yet hit**: this connects to Temporal synchronously during app startup, before `builder.Build()` - `depends_on: temporal` in `docker-compose.yml` only guarantees container start order, not that Temporal's server is actually accepting connections yet, so a race is theoretically possible (worked fine in testing; not hardened, since it's not an observed problem yet). Verified end-to-end: `POST /api/v1/orders` through the gateway resulted in a workflow whose ID exactly matched the new order's ID, completed automatically with no manual trigger, real payment/shipment responses embedded in the result.
**Real gap found this session, not yet fixed - the dual-write problem, live in the current code, not hypothetical**: `StartOrderFulfillmentWorkflowHandler.Handle` calls `_client.StartWorkflowAsync(...)` *synchronously, inside the same HTTP request* that creates the order, via MediatR's in-process notification publish. If that call fails for any reason (Temporal briefly unreachable, a transient gRPC error), the exception propagates all the way out through `mediator.Send(command)` in `OrderEndpoints.cs` uncaught -> the client gets a `500`. Worse: `_repository.CreateOrderAsync` already committed the order to Postgres *before* the publish is attempted, so the order now exists with no workflow ever started for it - and since a client retry with the *same* `Idempotency-Key` correctly returns the existing order with `WasCreated: false`, `OrderCreatedEvent` never gets published again on any future retry. The order is permanently orphaned. This is exactly the dual-write problem Stage 6's outbox pattern is designed to fix - not just for the eventual message-broker migration, but for this exact synchronous call too: write an `OutboxMessage` row in the same `SaveChangesAsync()` transaction as the order, let a separate background processor retry `StartWorkflowAsync` against that row until it succeeds, fully decoupled from the original HTTP request succeeding or failing.

## Stage 5: Compensation for the order -> payment -> ship flow (saga pattern)
**Goal**: Implement compensating actions for each failure point:
- Payment declined -> cancel the order (no shipment ever attempted).
- Shipping fails -> refund the payment (compensating call to payment-service) and cancel the order.
**Success Criteria**: Force a decline at the payment step and confirm the order ends up cancelled with no shipment attempted. Force a shipping failure and confirm the payment gets refunded and the order ends up cancelled — no step left half-done.
**Prior discussion — saga terminology**: settled on standard saga vocabulary before implementing - **compensable** transactions (can be cleanly undone, e.g. `ChargePaymentAsync` -> refund), the **pivot** transaction (the point of no return - here, `ShipOrderAsync`, since a physically shipped package can't be "un-shipped" by a DB write), and **retryable** transactions (after the pivot, not compensated on failure - just retried to success, must be idempotent). Also discussed a real-world refinement from Korean e-commerce (Lotte On): the pivot isn't always a single instant - there's often a blackout window (in-transit) where *neither* cancel nor return works, and the post-delivery "cancel" customers see is actually a structurally different process (return/반품) than pre-shipment cancellation, not the same compensating action run backward. **Deliberately out of scope for this stage**: modeling that richer in-transit/post-delivery-return distinction (a separate `Shipping` status distinct from `Delivered`, a distinct post-delivery return saga) - tracked as a real follow-on, not folded in here to keep this stage's scope to "build the cancel workflow" as asked.
**Anticipated (not premature) scope note**: `payment-service`'s Stage 3 stub is deliberately stateless (mirrors `user-service`'s dice-roll design) - refund requires remembering which specific payment to reverse, which that design has no way to do. Expect to upgrade `payment-service` here to track charge/refund state, likely a simple in-memory `Dictionary<Guid, PaymentStatus>` rather than a full Postgres + Clean Architecture rebuild - we already thoroughly mined that pattern via `order-service`; the novel part of this stage is the saga/compensation flow itself, not re-deriving persistence architecture. Deliberately not built ahead of this stage despite being foreseeable now.
**Status**: In Progress

### Stage 5c: Compensation activities in order-workflow-worker
**Goal**: `CancelOrderAsync(Guid orderId)` (`PATCH order-service`, `{Status: "Cancelled"}`) and `RefundPaymentAsync(Guid orderId)` (`POST` payment-service's new refund endpoint), both `[Activity]`-decorated alongside the existing ones in `OrderActivities.cs`.
**Idempotency built in from the start**: `CancelOrderAsync` treats a `409` (order already `Cancelled`) as success, not a failure - covers the duplicate-Activity-dispatch scenario walked through earlier (a false Temporal timeout causing the same compensation to run twice). `RefundPaymentAsync` treats both `404` (nothing was ever charged) and `409` (already refunded) as success - the former is the "defensive refund attempted, nothing to reverse" case from the saga discussion, the latter is the same duplicate-dispatch case as cancellation. Only a genuine unexpected error (5xx, network failure) throws and lets Temporal's `RetryPolicy` handle it.
**Status**: Implemented (`dotnet build` green). Both Activities registered on the worker but not yet called from anywhere - `OrderFulfillmentWorkflow` doesn't invoke them until Stage 5d wires them in, so there's nothing to live-test yet in isolation.

### Stage 5d: Wire compensation into OrderFulfillmentWorkflow
**Goal**: Catch a failure after `ChargePaymentAsync` exhausts its retries -> call `CancelOrderAsync` -> rethrow, so the workflow correctly ends `Failed` (superseded from an earlier draft that returned `Completed` - see the resolution below, decided against Temporal's own official guidance rather than by preference). Catch a failure after `ShipOrderAsync` exhausts its retries -> call `RefundPaymentAsync` then `CancelOrderAsync` -> rethrow, same reasoning. If a compensating Activity itself throws, let that propagate as a genuine workflow Failure - no silent swallow, matching the earlier discussion that compensations aren't guaranteed to succeed either.
**Refinement - compensation must be conditional on the *kind* of payment failure, not just failure/success**: a clean decline (`402`, insufficient balance) is a definitive, synchronous answer - no ambiguity about whether money moved, so no refund attempt is needed at all, just cancel. A network/timeout failure is genuinely ambiguous - the charge may have silently succeeded despite the workflow observing a failure (the same false-timeout mechanics established for `CancelOrderActivity`/at-least-once delivery), so only *this* case should trigger a defensive `RefundPaymentAsync` before cancelling. Mechanism: `ChargePaymentAsync` throws `ApplicationFailureException(message, nonRetryable: true)` on a `402` (Temporal never retries a definitive decline, and the workflow can recognize this specific failure type) vs. throwing normally on a network/timeout error (goes through the existing `RetryPolicy`, and only a genuine retries-exhausted `ActivityFailureException` means "ambiguous, might have charged, refund defensively"). `OrderFulfillmentWorkflow`'s catch logic branches on *which kind* of failure it caught, not just whether `ChargePaymentAsync` threw at all - discussed via the real industry pattern (Stripe's `Idempotency-Key` header, permanent-vs-transient error classification) rather than assumed.
**Success Criteria**: Force a clean payment decline -> order ends `Cancelled`, no shipment ever attempted, no refund call ever made, workflow completes (not Failed). Force a payment-step network/timeout failure (simulated) -> `RefundPaymentAsync` is called defensively even though no real charge exists, resolves as a safe no-op via the `404` handling, order ends `Cancelled`, workflow completes. Force a shipping failure -> payment refunded (a real charge existed), order ends `Cancelled`, workflow completes.
**Bug found and fixed during design review, before any code was written**: the first draft had `MarkOrderShippingAsync` inside the *same* `try` as `ChargePaymentAsync`/`ShipOrderAsync`. If `MarkOrderShippingAsync` failed - even though the real shipment had already gone out - the generic catch-all would have refunded and cancelled an order that was physically in transit. Fixed by splitting the `try` scope: only the genuinely compensatable steps (charge, ship) are inside it; `MarkOrderShippingAsync` sits after it entirely, uncaught, with its own more patient `PostPivotActivityOptions` (`MaximumAttempts: 10` vs `3`) - a post-pivot failure must be retried to success or escalated, never compensated. Cross-checked against a reference saga pattern the user provided (`ReserveInventory`/`AuthorizePayment` -> pivot -> `SendConfirmationEmail` with `MaximumAttempts: 10`), which uses the identical phase-boundary structure.
**Second fix**: the `"PaymentDeclined"` string tying `ChargePaymentAsync`'s thrown `ApplicationFailureException.ErrorType` to the workflow's `catch (...) when (...)` pattern match was a bare literal in both places, with nothing enforcing they stay in sync. Extracted to `OrderActivities.PaymentDeclinedErrorType` (a `public const string`), referenced from both places instead of duplicated.
**Resolved: Completed vs. Failed.** Checked against Temporal's official Saga Pattern documentation directly rather than guessing: *"Always re-throw the original exception after running compensations so the Workflow reports the correct failure reason."* The reasoning matters more than the rule - `Failed` here doesn't mean "something is broken," it means "the workflow's primary business goal (fulfilling this order) wasn't achieved," which is accurate even when compensation itself succeeded cleanly. The docs draw a clean separation: the *business process* failing is reported as `Failed` (rethrow); *compensation logic* failing is handled separately (log, don't let it change the reported outcome). Both catch blocks now end with `throw;` (bare rethrow, preserves the original exception) instead of returning a descriptive `Completed` string.
**Design note surfaced this session**: `CancelOrderAsync` isn't really a compensation in the strict sense `RefundPaymentAsync` is - it doesn't reverse a side effect *this workflow* caused (the order was created by `order-service`'s own command handler, before this workflow ever started). It's closer to `MarkOrderShippingAsync`'s sibling - both are the workflow reporting its outcome back to `order-service` (success vs. failure), not reversing a step in this workflow's own sequence. Doesn't change the implementation, but matters if a `Saga`/compensations-list is ever introduced later - `CancelOrderAsync` wouldn't belong in that list the way `RefundPaymentAsync` would.
**Handling when a compensating Activity itself fails** (distinct from the forward-path failure that triggered compensation in the first place):
1. **Activity-level retries** (already in place) - `RefundPaymentAsync`/`CancelOrderAsync` share the same `ActivityOptions`/`RetryPolicy` as the forward path, so transient failures are retried automatically before anything reaches the workflow.
2. **Asymmetric, more patient retries for compensations, if this becomes a real problem** - not yet built, but the same reasoning as `PostPivotActivityOptions`: giving up on a refund is worse than giving up on shipping, so a compensating Activity arguably deserves a higher `MaximumAttempts` than the forward path's `3`, the same way post-pivot activities got `10`.
3. **Temporal's durability as the real backstop, not a code trick** - a Workflow can stay open indefinitely (a `Workflow.DelayAsync` retry loop, or waiting on a Signal from an operator who resolved it out-of-band) rather than needing to resolve a stuck compensation synchronously.
4. **A reconciliation job is the honest, final backstop** - see the "Future experiment - reconciliation against the bank's ledger" note below Stage 5d; every production payment-architecture reference converged on this same term. No code path makes "the refund keeps failing" self-healing forever.
**Resolved: sequential-compensation gap, refund-failure handling.** Discussed at length and deliberately chose the *simpler* of two designs after a real objection: initially considered adding a new `"RefundFailed"` order status + `MarkRefundFailedAsync` Activity (mirroring `CancelOrderAsync`) so the order's own data would honestly reflect a stuck refund - rejected specifically because it adds another failable HTTP call for marginal benefit ("we are going to add more failable paths"). Went with the simpler alternative instead: `RefundPaymentAsync` is now wrapped in its own inner `try/catch`. If it fails, `CancelOrderAsync` is deliberately **not** called - marking the order `"Cancelled"` while a refund is stuck would be actively misleading (implies nothing is owed, when something is). The order correctly stays `"Placed"`, same as the original gap, but the workflow's `Failed` status (from the outer rethrow) is the actual signal - no new order-service surface, no new status, no new failable path for the domain model itself.
**Layer 2 - human notification, added on top**: new `NotifyOpsAsync(Guid orderId, string reason)` Activity, POSTs `{orderId, reason, timestamp}` to a configurable `OPS_WEBHOOK_URL` (webhook.site during development). Called specifically when `RefundPaymentAsync` fails - this is the one case that genuinely needs a human, versus a clean decline (nothing to refund) or a normal shipping failure (refund succeeded, order correctly cancelled). Chosen over two alternatives: Layer 1 (log only, rely on Temporal UI) and Layer 3 (full Prometheus/Grafana/PagerDuty alerting, real infrastructure out of scope for this project) - Layer 2 is the first tier that's an actual active notification rather than something requiring someone to go looking.
**Second-order bug caught before it shipped**: the first draft called `NotifyOpsAsync` directly inside the refund-failure catch, with no protection of its own - if `NotifyOpsAsync` itself failed, *its* exception would replace the original refund-failure exception as the workflow's reported failure reason, silently obscuring the real root cause, and no notification would even go out. Fixed by wrapping `NotifyOpsAsync` in its own innermost try/catch that logs via `Workflow.Logger.LogError` (deterministic, replay-safe, and in a real deployment tagged with `WorkflowId`/`RunId` and shipped to log aggregation) and continues regardless - the original refund-failure exception is always what gets rethrown, `NotifyOpsAsync`'s own failure never overwrites it.
**Status**: Complete. All catch-block fixes verified live: clean decline (order `Cancelled`, no shipment, no refund attempted, workflow `Failed`, benign `DbUpdateException` idempotency-replay log noise correctly identified as non-bug along the way), shipping-failure-with-successful-refund (order `Cancelled`, workflow `Failed`), and refund-failure specifically (temporarily forced `payment-service`'s refund endpoint to always `500` - confirmed `NotifyOpsAsync` fired with the exact expected payload on webhook.site, order correctly stayed `"Placed"` rather than falsely `"Cancelled"`). `docker-compose.yml` also hardened this session: `temporal`'s healthcheck fixed (was wrongly checking Postgres readiness via `pg_isready` inside the Temporal server container; now `temporal operator cluster health`), `order-service`'s `depends_on` converted to `condition: service_healthy` on `temporal` (fixes the `ConnectionRefused` race hit live), and `gateway`'s Traefik given `--providers.docker.exposedbydefault=false` (fixes `order-workflow-worker`'s "port is missing" error and the same latent issue for every other non-HTTP-routed container).

### Stage 5e: Required Idempotency-Key across order-service and payment-service
**Goal**: Discovered while manually reproducing the double-charge bug (confirmed live: two identical `POST /api/v1/payments` calls both returned `200 Charged`, no protection at all) and while setting up Stage 5's idempotency work - `order-service`'s `POST /api/v1/orders` silently allowed order creation with *no* `Idempotency-Key` header at all (treated as `null`, no dedup). Decided or deliberately: require the header on both endpoints rather than leave it optional (Stripe leaves it optional; we chose not to, so no caller can silently skip dedup protection).
**order-service**: `POST /api/v1/orders` returns `400` if `Idempotency-Key` is missing or empty, before reaching the command handler.
**payment-service**: `POST /api/v1/payments` returns `400` if `Idempotency-Key` is missing. New `ConcurrentDictionary<string, ChargeAttempt>` keyed by the idempotency key, recording both outcomes (declined and charged) the first time a key is used - mirrors Stripe's actual documented behavior ("saves the resulting status code and body of the first request... regardless of whether it succeeds or fails"). A reused key with matching `orderId`/`amount` replays the original result (no second charge, no re-rolled decline); a reused key with different content returns `409`. Also removed an accidental, unused `Idempotency-Key` read that had been added to the refund endpoint by mistake mid-session - refund keeps its original, sufficient protection via the `409` "already refunded" check on its own `PaymentRecord.Status`.
**order-workflow-worker**: `ChargePaymentAsync` now sends `Idempotency-Key: {orderId}` (built via an explicit `HttpRequestMessage` instead of `PostAsJsonAsync`, since the header is per-request and can't go on the shared `HttpClient`).
**Design note surfaced during this stage**: `payment-service` does not and should not need to know `order-service`'s order status (or vice versa) to do its own job - each service is the sole authority over its own state (`Charged`/`Refunded` vs `Placed`/`Shipping`/`Cancelled`), coordinated only by the workflow calling each independently. Same bounded-context principle as the earlier "shared entity across services" discussion, applied concretely here.
**Success Criteria**: `POST /api/v1/orders` with no `Idempotency-Key` -> `400`. `POST /api/v1/payments` with no `Idempotency-Key` -> `400`. Same key + same `orderId`/`amount` sent twice -> second response identical to the first, only one entry in the `orderId`-keyed `payments` dictionary (no second charge). Same key + different content -> `409`.
**Status**: Complete. Verified live by the user against `payment-service`: same `Idempotency-Key` + same `orderId`/`amount` sent twice -> both calls returned identical `200 Charged` (only one real charge recorded, second call replayed the cached result rather than re-processing); same key + different content -> `409 "Idempotency-Key was already used for a different request"`. The `400`-on-missing-header checks (both services) weren't separately exercised live but are simple, low-risk guard clauses matching the already-proven `order-service` Stage 1f pattern.

## Stage 6 (stretch goal): Migrate the flow to pub-sub (includes the outbox pattern, merged from Stage 1g)
**Goal**: Once Stages 4-5 work as synchronous orchestration (direct HTTP calls), migrate the same order -> payment -> ship flow to an event-driven/pub-sub model on a message broker (RabbitMQ or Kafka, added to docker-compose). `order-service` publishes `OrderCreated`; `payment-service` subscribes and publishes `PaymentCharged`/`PaymentDeclined`; `ship-service` subscribes to `PaymentCharged`; compensation (Stage 5) becomes event-driven too (e.g. `PaymentDeclined` triggers an `OrderCancelled` handler instead of a direct function call).
**Outbox pattern, built as part of this stage, not before**: `CreateOrderCommandHandler` writes an `OutboxMessage` row (representing `OrderCreated`) in the *same* `SaveChangesAsync()` call as creating the order - guarantees the event is never lost even if the actual broker publish fails independently of the DB commit (the dual-write problem, this time with a *real* second system - the broker - not just a second table). A background processor (hosted service) reads unprocessed outbox rows and publishes them to the chosen broker, marking them processed only after a confirmed publish. Building this now, with a real broker and real consumer already in place, avoids re-testing atomicity we already proved in Stage 1e and avoids locking in a message schema before the broker choice is made.
**Success Criteria**: The same end-to-end success and compensation scenarios from Stages 4-5 still work, now via published/subscribed events instead of direct calls. Additionally: force a crash between the DB commit and the broker publish, and confirm the outbox row survives to be retried/published on recovery rather than the event being silently lost.
**Discussion to have once this is running**: compare the two implementations side by side and cover the actual trade-offs, not just "pub-sub is better" —
- **Why employ pub-sub at all**: decoupling (a service being briefly down doesn't block the caller — the event just waits in the queue), easier fan-out (new subscribers, e.g. an analytics service listening to `OrderCreated`, can be added without touching the existing flow), and it's the pattern real systems (e.g. Karrot, per the earlier research: RabbitMQ for internal events, Kafka for cross-company events) actually use for this kind of cross-service coordination.
- **What it costs**: messages can be delivered more than once or out of order (subscribers need to be idempotent, which the synchronous version never had to worry about), a failure is no longer "the HTTP call returned an error" — it's "nothing happened yet, or something happened twice," and tracing an order's full journey end-to-end gets harder (no single call stack, need correlation IDs and log aggregation across services).
- **When each is the right choice**: orchestration/synchronous is easier to reason about and debug for a small number of tightly-coupled steps (like our 3-step flow) — pub-sub earns its complexity once you have many subscribers, need resilience to a dependent service being down, or the steps genuinely don't need to happen in lockstep.
